## 2. بنية المصدر والتحقق من التحديث

يقع `app/` بجانب `render.yaml` و`requirements.txt` و`agents.json` في جذر المستودع. يعتمد البناء على هذه الملفات مباشرة. حزمة ZIP للتسليم فقط؛ لا تُستخرج أثناء بناء Render، ولا يُفترض أن حزمة قديمة تحتوي آخر تحديث.

للحصول على نسخة محلية أول مرة:

```bash
git clone https://github.com/aihub1971-code/AIHUB.git
cd AIHUB
```

إذا كانت لديك نسخة عمل، استخدمها مع حماية التغييرات المحلية. أنشئ فرعًا للتعديلات الجديدة، وراجع فرق المصدر والاختبارات قبل دمجه في `main`؛ لا تستخدم `force push` على الفرع القائم.

من جذر المشروع بعد إعداد Python 3.12 والبيئة الافتراضية:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest
node --check app/static/app.js
node tests/test_ui_news.js
python scripts/validate_blueprint.py
python scripts/package_handoff.py --output dist/AI_HUB_Project.zip
```

فاحص Blueprint يقرأ [مخطط Render الرسمي](https://render.com/schema/render.yaml.json) ويختبر بنية YAML؛ لا ينشئ خدمة ولا يزامن حسابًا. للعمل دون إنترنت مرّر نسخة محفوظة من المخطط إلى `--schema`. إذا كانت Render CLI مثبتة بإصدار 2.7.0 أو أحدث، يدعم [المرجع الرسمي](https://render.com/docs/blueprint-spec) أيضًا `render blueprints validate render.yaml`.

### GitHub Actions

يشغّل `.github/workflows/tests.yml` فحص Python والاختبارات وفحص JavaScript واختبارات عارض الأخبار والتحقق من Blueprint، ثم يجهّز حزمة حديثة من المصدر. يستخدم بيانات اصطناعية ولا يحتاج إلى مفتاح OpenAI أو أسرار Render. يتطلب فحص الواجهة Node.js، لكنه ليس مطلوبًا لتشغيل خدمة Python على Render. يحفظ Artifact مرتبطًا بمعرّف commit لمدة 7 أيام. تُراجع نتيجة التشغيل الخاصة بالـcommit المراد نشره؛ نجاح خط الأساس السابق لا يثبت صحة تحديث البحث الجديد.

الإعداد `autoDeployTrigger: checksPass` يتبع تحديثات الفرع بعد نجاح فحوص CI. قد يمنع تعذر الوصول إلى مخطط Render اجتياز فحص Blueprint حتى إعادة المحاولة بنجاح. لا تبدأ نشرًا يدويًا لتجاوز فحص فاشل دون فهم سببه.

## 3. البنية والتكلفة

| المكوّن | الإعداد المتحقق منه |
|---|---|
| خدمة الويب | `ai-hub`، Python، Frankfurt |
| خطة الحوسبة | `0.5c-512mb`؛ 0.5 CPU و512 MB RAM |
| الفرع | `main`، والنشر التلقائي بعد نجاح الفحوص |
| النسخ / العمال | نسخة واحدة، وعامل Uvicorn واحد |
| القرص الدائم | `ai-hub-data`، 1 GB |
| مسار القرص | `/var/data/ai-hub` |
| قاعدة البيانات | `/var/data/ai-hub/ai-hub.sqlite3` |
| فحص الصحة المطلوب | `/health` |
| حالة المجدول عند البداية | `SCHEDULER_ENABLED=false` |

السعر المعروض عند إنشاء الخدمة: **7 دولارات شهريًا للحوسبة + 0.25 دولار شهريًا لقرص 1 GB = 7.25 دولارات شهريًا**. هذا سعر الاستضافة والقرص قبل الإضافات والضرائب وتكلفة OpenAI، وليس إجمالي فاتورة المشروع. مرجع [أسعار Render](https://render.com/pricing)، و[مواصفات الحوسبة](https://render.com/docs/compute-plans)، و[الأقراص الدائمة](https://render.com/docs/disks). حد ميزانية التطبيق لا يوقف رسوم الاستضافة.

هذا التصميم للمالك الواحد وحمل محدود. العدد 50 سقف محاولات يومي، وليس نتيجة اختبار تحميل أو وعدًا بإكمال 50 تقريرًا ضمن الميزانية. تتأثر السعة بطول المهمة وزمن البحث والتوليد والأدلة المتاحة.

## 4. تطبيق إصدار OpenAI على الخدمة الحالية

1. تحقق من وجود تحديث 1.3.0 الخاص بعرض الأخبار والتحليل وجولتَي البحث في الفرع الذي تتبعه الخدمة، ومن نجاح CI الخاص به.
2. راجع Blueprint القائم في مساحة **AI's workspace** والخدمة ذات المعرّف أعلاه. أعد مزامنة إعداداته بعد تحديث `render.yaml` عند الحاجة؛ لا تنشئ نسخة ثانية من الخدمة.
3. يضبط المالك ثلاثة حقول خاصة فقط في **Environment**: `APP_USERNAME` و`APP_PASSWORD` و`OPENAI_API_KEY`. البحث والتوليد يستخدمان مفتاح OpenAI نفسه. تُحفظ القيم الموجودة الصالحة؛ لا حاجة إلى استبدالها لمجرد تحديث الكود.
4. راجع `OPENAI_MODEL_NAME` والأسعار وحدود البحث والميزانية بحسب `.env.example` و[دليل التشغيل](OPERATIONS_AR.md)، مع إبقاء `SCHEDULER_ENABLED=false`.
5. تحقق من أن القرص مضاف فعليًا وأن قاعدة SQLite تقع تحت `/var/data/ai-hub`، ثم تابع حالة النشر وسجله في Render.
6. بعد أن تصبح النسخة الجديدة حية، افحص `/health`، وسجّل الدخول، وراجع `/v1/system`. هذه فحوص تهيئة واستجابة؛ الاختبار الحي المحدود في الخطوة التالية هو الذي يفحص صلاحية المفتاح والأداة.
7. نفّذ تقريرًا حيًا واحدًا وراجع مصادره وتواريخه وعدده وحالة الاستخدام، ثم تأكد من بقاء السجل بعد إعادة التشغيل قبل تفعيل أي جدول.

الحقل `sync: false` يطلب قيم الأسرار أثناء إنشاء Blueprint أول مرة فقط. عند تغيير الأسرار أو إضافة حقل خاص لاحقًا، استخدم صفحة **Environment**؛ المزامنة لا تطلبه مجددًا. راجع [آلية أسرار Blueprint](https://render.com/docs/blueprint-spec#prompting-for-secret-values). لا تضع القيم في YAML أو ملفات المصدر أو المحادثة.

## 5. الترحيل من طريقة البناء القديمة

اكتمل نشر المصدر المباشر في المستودع. إذا وُجدت خدمة أخرى ما زالت تستخرج حزمة مضغوطة أثناء البناء، يجب أن تشير إلى الفرع الذي يحتوي `app.main:app`، وتستخدم أوامر البناء والتشغيل أعلاه، مع Root Directory الصحيح. لا يتطلب الإصدار طبقة ملفات بديلة أو مجلدًا أنشأته حزمة قديمة.

احتفظ بنسخة متسقة من أي بيانات إنتاج قبل نقل مسارها. هذا المشروع لا يستورد تلقائيًا تاريخ تقارير من نظام سابق غير مطابق. بيانات الدخول الحالية هي `APP_USERNAME` و`APP_PASSWORD`.

يحدد `.python-version` سلسلة Python 3.12. إذا وُجد متغير `PYTHON_VERSION` قديم في الخدمة فإنه يتقدم على الملف؛ راجع اختياره حسب [ترتيب الأولوية الموثق](https://render.com/docs/python-version).

## 6. الديمومة وإعادة النشر

يتوفر قرص Render للخدمة أثناء التشغيل فقط؛ لا يكون متاحًا أثناء البناء أو أوامر ما قبل النشر أو خدمة أخرى. لهذا تُهيأ SQLite عند بدء التطبيق، وتعمل الخدمة بعامل واحد ونسخة واحدة. لا تضف عدة عمال أو نسخ دون إعادة تصميم التخزين وتنسيق الجدولة.

تسبب إعادة النشر توقفًا قصيرًا لخدمة القرص. لا يعتمد المجدول على تعويض كل زمن الانقطاع؛ يتجاوز المواعيد الأقدم من مهلة السماح. احتفظ بنسخ SQLite متسقة وانقلها إلى وجهة خاصة خارج قرص الخدمة؛ راجع [دليل التشغيل والنسخ الاحتياطي](OPERATIONS_AR.md).

## 7. فحص الخدمة بعد النشر

مع بيانات دخول المالك محفوظة في `.env` محلي خاص:

```bash
python scripts/smoke_test.py --base-url https://ai-hub-vc8w.onrender.com
```

الفحص السابق للقراءة فقط. لتقرير حي واحد قابل للفوترة بعد اكتمال نشر التحديث:

```bash
python scripts/smoke_test.py --base-url https://ai-hub-vc8w.onrender.com --live --agent iran-news
```

راجع معرّف الطلب والأرشيف قبل تكرار محاولة انتهت مهلتها. سجّل commit المنشور ونتيجة الفحص الفعلية في `docs/VALIDATION_AR.md`؛ وجود هذه الأوامر لا يعني أنها نُفذت.
